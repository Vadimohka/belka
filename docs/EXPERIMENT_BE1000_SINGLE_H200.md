# BE1000: сравнение локальных моделей на одной H200

Дата проектирования: 2026-10-28.
Статус: **протокол эксперимента, не отчёт о выполненном обучении**.
Проверенная программная база: `840a3f4cdba1194e09bf2f776c0b7dfd880caf34`.

Этот документ не запускает подготовку, probe, обучение или inference. Он не добавляет готовый набор из 1000 вопросов и не объявляет существующие runner полноценным измерителем качества. Гиперпараметры ниже — исходные предложения для выбора на development-данных, не измеренный оптимум. Ревизии внешних весов, конкретный test manifest, бюджет GPU и протокол разметки необходимо зафиксировать до запуска.

## 1. Что именно проверяем

Три основных результата по сценарию владельца:

| ID | Система | Что измеряется |
|---|---|---|
| A0 | Небольшая готовая instruction-модель без нашей адаптации | Исходная способность отвечать по-белорусски |
| B1 | Тот же checkpoint после continued pretraining на белорусском корпусе и общего белорусского SFT | Результат нашего пакета адаптации |
| C1 | Belka со случайной инициализацией, после pretraining на том же корпусе и общего SFT | Практическое качество модели, обученной нами с нуля |

A0 и B1 обязаны происходить от одного и того же checkpoint с одним исходным токенизатором. Нельзя незаметно заменить слабую модель на другую между измерениями. Под «слабой» здесь понимается небольшая по размеру контрольная модель; её слабость именно на белорусском ещё предстоит измерить. Не выбирать модель по худшему результату на финальных 1000 заданиях.

**B1 − A0** измеряет весь пакет CPT + SFT, а не чистое влияние сырого корпуса. **C1 против B1** сравнивает системы с разной историей обучения, а не изолированное качество архитектур. Готовая модель уже имеет внешнее предобучение и instruction tuning. Это преимущество нужно указывать, а не пытаться объявить условия полностью равными.

Внешняя адаптируемая модель остаётся отдельным baseline. Belka не получает её веса и не перестаёт быть проектом обучения с нуля.

### Недорогие, но важные контроли

| ID | Дополнительная точка | Назначение |
|---|---|---|
| A1 | Исходный checkpoint + только тот же SFT, без CPT | Сравнение B1 с A1 отделяет наличие этапа корпусной адаптации при одинаковой последующей SFT-процедуре |
| B0 | Checkpoint непосредственно после CPT, до SFT | Сравнение с A0 показывает действие CPT без добавленного нами SFT; помогает увидеть потерю формата ответа |
| C0 | Belka base до SFT | Необязательная диагностика вклада instruction tuning; для сырого base отдельно полезна оценка продолжения текста |

Рекомендованный отчёт показывает A0/B1/C1 как три основных столбца, A1/B0 — как контрольные. Для пяти точек получится 5000 ответов на **одни и те же 1000 заданий**, а не пять разных наборов. B0 уже возникает во время B1; нужен дополнительный inference, не отдельное CPT-обучение. A1 требует только небольшой SFT-запуск.

## 2. Выбор моделей

Основной вариант для текущего профиля Belka:

- baseline: `Qwen/Qwen2.5-1.5B-Instruct`, 1,54 млрд параметров по карточке автора;
- Belka: `h200_max`, 1 384 122 122 параметра по репозиторному планированию.

Более дешёвый пилот, с которым нельзя смешивать итоговые scores основной конфигурации:

- `Qwen/Qwen2.5-0.5B-Instruct`, 0,49 млрд параметров;
- Belka `h200_quality`, 536 871 738 параметров.

Qwen2.5 выбран как фиксированный компактный instruction-baseline без дополнительного переключателя thinking, не как заявление о самой новой или самой слабой модели. Размеры внутри пары близки, но не одинаковы. Для Qwen сохраняются исходный словарь, специальные токены и chat template. Токенизатор Belka нельзя подставлять в Qwen, даже при одинаковом размере словаря.

Источники: [0.5B](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct), [1.5B](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct), [Belka profiles](../configs/profiles_h200.yaml), [планирование H200](H200_TRAINING.md).

Перед скачиванием/запуском фиксируются полный revision SHA каждого внешнего репозитория, hashes файлов весов и токенизатора, precision, лицензия из выбранной ревизии. Изменяемое имя `main` не является достаточной идентичностью checkpoint. Никакие веса для этого документа не скачивались.

## 3. Что изменилось в свежем репозитории

В текущем коде уже есть:

- `ops/local/run_belka_h200_maxquality.sh`: отдельные команды `plan/check/probe/execute`, один GPU, BF16;
- `tools/training_plan.py`: привязка к runtime, corpus/tokenizer/SFT inventories, budgets и аппаратному отчёту;
- подготовка расширенного корпуса, train-only BPE, перенос готовых артефактов;
- общий HTTP-клиент для native Belka и OpenAI-compatible локальных endpoints;
- acquisition manifest и runner BelarusianGLUE;
- HF custom-code export Belka для reference-инференса.

По опубликованным README/отчётам подготовлено 3 274 476 train и 48 740 validation документов; 1 635 285 758 train-токенов и 17 977 093 validation-токена с BOS, измеренных **токенизатором Belka BPE32768**. Это прочитанные сведения предыдущей подготовки, не новый проход по данным владельца. Число Qwen-токенов из этих чисел не следует.

Предыдущий вывод о неопубликованном пути подготовки не описывает эту новую версию. При этом готовность native Belka-подготовки не равна наличию полного трёхмодельного эксперимента.

Оценщик `eval/run_openai_compatible_eval.py` проверяет язык и ключевые слова, а не фактическую правильность каждого ответа. Он открывает output на перезапись, не реализует возобновление по проверенной идентичности опыта и не сохраняет все данные generation/finish_reason. `eval/protocol.py` возвращает только текст. Эти ограничения существенны для BE1000.

`tools/run_belarusianglue_eval.py` полезен как источник task-specific prompts и метрик. Необходимо сохранять его честную оговорку: собственный zero-shot протокол не равен официальному leaderboard score.

`deploy/serve_vllm.sh` явно отклоняет неподдерживаемый native Belka adapter. Не пытаться обслуживать Belka как Qwen или Llama. Для основного сбора ответов использовать native Belka server; для Qwen — его отдельный локальный backend. Одинаковый HTTP-клиент не делает kernels и скорость двух backend одинаковыми.

## 4. Не смешивать CPT и SFT

CPT (continued pretraining) — следующий этап next-token обучения существующей модели на обычном тексте. SFT — обучение на инструкциях/диалогах с правильными масками ответов. Обычный Parquet-корпус нельзя назвать набором вопрос–ответ только сменой названия файла.

Предлагаемые цепочки:

```text
Qwen instruct исходный ──────────────── A0
          ├─ общий SFT ─────────────── A1
          └─ белорусский raw corpus ── B0 ── общий SFT ── B1

Belka random init ── тот же raw corpus ── C0 ── общий SFT ── C1
```

Для обеих адаптируемых систем используется одна неизменяемая последовательность исходных документов. Каждый backend токенизирует текст своим токенизатором. Одинаковое число tokenizer tokens не означает одинаковый объём текста. Отдельно учитывать уникальные документы, UTF-8 байты, предъявленные байты, content tokens, BOS/EOS, число проходов и GPU-время.

Для первой версии рекомендуется заранее установить общий максимум **один полный проход корпуса** для B0/C0: это ограниченный matched-exposure опыт, не обещание достаточного обучения Belka. Сохранить checkpoints по заранее выбранным долям прохода. Выбор итогового checkpoint — только по заранее определённому правилу на development; при выборе разных долей фактическая экспозиция различается и должна быть указана. Отдельно можно сравнить обе системы на последнем checkpoint одного полного прохода без выбора по test.

Профили Belka по умолчанию предлагают три прохода. Если требуется основной трёхпроходный запуск, это заранее зафиксированный второй режим: дать обеим системам тот же максимум предъявлений документов или честно назвать сравнение recipe-optimized, а не equal-exposure. Не продлевать schedule после просмотра финальных scores и не интерпретировать повторные проходы как новые независимые данные.

Оптимизаторы/learning rate не обязаны совпадать: дообучение готовых весов и обучение с нуля имеют разные исходные условия. Для Qwen полный fine-tuning предпочтительнее смешивания дополнительного фактора QLoRA в основном опыте. LoRA — допустимая отдельная абляция, не скрытая замена CPT-рецепта.

Предложение для короткого development-пилота Qwen: BF16 autocast, AdamW, context 2048, learning rate из `{5e-6, 1e-5, 2e-5}`, warmup 2%, decay 0.01, clipping 1.0. Это сетка выбора, не гарантия оптимальности. Самый дешёвый фиксированный старт — 1e-5 без выбора по test. Для Belka сохранить native optimizer/scheduler выбранного профиля; не переносить learning rate Qwen в nanochat.

В A1/B1/C1 использовать одинаковые диалоги, их split, порядок/seed и ограничение числа предъявлений. Chat templates и числа токенов различаются, поэтому одинаковые 14 optimizer steps не являются доказательством одинакового SFT exposure. Текущий гайд описывает всего 430 train / 140 validation диалогов: этого нельзя объявлять достаточным для универсального instruction-following. Первый опыт может использовать их как есть; расширение SFT — отдельная версия опыта.

## 5. Финальные 1000 заданий

До обучения формируются `be1000-test.jsonl`, отдельный development-набор (предложение: 200 заданий), инструкция оценщикам и manifests. Ни тест, ни эталонные ответы, ни парафразы семейства теста не поступают в CPT, SFT или обучение токенизатора.

Предлагаемый состав теста:

| Блок | Количество | Оценка |
|---|---:|---|
| BelarusianGLUE, по 100 на пять задач | 500 | Gold-label accuracy; task-specific MCC/F1 и format compliance |
| Понимание нового текста и вопросы по нему | 150 | Ответ по приведённому контексту, полнота и отсутствие выдумок |
| Белорусская грамматика, лексика и редактирование | 100 | Эталон/рубрика, допустимые варианты |
| Инструкции, структурированный ответ, краткое изложение | 100 | Формальные ограничения и смысловая оценка |
| Проверяемые факты о Беларуси | 50 | Датированный источник и правильность; без неограниченных current-events вопросов |
| Простая математика и логика на белорусском | 50 | Правильный результат и выполнение задания |
| Устойчивость белорусского ответа | 50 | Языковая последовательность, без награды за бессодержательный ответ |
| **Всего** | **1000** | |

Для GLUE: 100 CoLA (50 in-domain + 50 out-of-domain), 100 BeRTE-WD, 100 BeSLS, 100 BeWiC, 100 BeWSC **в одном выбранном представлении**. Выборка воспроизводимая и сбалансированная по gold labels, с зафиксированными исходными IDs. Проверить доступность классов до заморозки. `bewsc_as_wnli` и `bewsc_as_wsc` не считать разными независимыми заданиями. При связанных примерах использовать общий family_id.

Существующий acquisition manifest описывает 2210 записей на split с дублированием WSC-представлений. Взять 500 для собственного теста можно, но результат надо назвать `BE1000 / BelarusianGLUE subset`, не официальной итоговой метрикой BelarusianGLUE. Основной источник: [репозиторная карточка](../eval/datasets/belarusianglue/README.md), [статья авторов](https://aclanthology.org/2025.acl-long.25/).

Остальные 500 заданий должны быть написаны/проверены отдельно. Не размножать существующие 209 holdout prompts шаблонными парафразами ради числа 1000. Не брать 570 SFT-диалогов как тест. Шаблонные семьи, один исходный документ и варианты одной задачи должны оставаться в одном split.

Контекстные задания получают новые тексты, отсутствующие в train. Для закрытого вопроса о факте присутствие самого факта в корпусе не равно утечке: проверять совпадение формулировок, эталонных ответов/длинных фрагментов и происхождение. Вопросы о дословно показанном train-документе можно демонстрировать отдельно как in-corpus recall, но не выдавать за held-out generalization.

Нужно заранее определить допустимость наркамаўкі/тарашкевіцы, собственных имён, цитат и коротких числовых ответов. `0`, `1` или правильное число не должно проигрывать из-за отсутствия белорусских букв.

## 6. Защита от утечек и выбора по финальному тесту

1. Заморозить IDs, категории, family/source IDs, вопросы, рубрики и references до inference A0.
2. Сверить новый набор с corpus train, validation, всеми SFT-ролями и доступной историей обучения Belka-tokenizer. Exact checks дополнить длинными нормализованными фрагментами и разбором кандидатов; не объявлять такую проверку доказательством отсутствия любых смысловых утечек.
3. Не менять готовое поколение данных на месте. При найденном реальном пересечении создать новую ревизию и обновить доказательства; при необходимости заново обучить Belka BPE только на её train. Предыдущий clean report для другого набора вопросов не покрывает автоматически новый BE1000.
4. Получить A0, но хранить ответы/gold test закрытыми для настройки до завершения выбора B/C. Для решений использовать только development. Если test уже разбирали и меняли по нему рецепт, честно считать его development и выделить новый финальный набор.
5. У внешнего Qwen нет полного доступного реестра предобучающих документов: доказать отсутствие публичного benchmark в исходных весах нельзя. Это отдельное ограничение; новые авторские вопросы уменьшают, но не обнуляют риск.

## 7. Одинаковый протокол генерации

Предложение для основной оценки: greedy decoding (`do_sample=False` / temperature 0 с проверенной семантикой backend), одинаковая инструкция на белорусском, без инструментов, retrieval, web, автоматического исправления ответов и model-specific подсказок.

Смысл messages одинаковый, технический template — родной для каждой модели. Вопросы и короткая общая инструкция задаются по-белорусски. Не давать Qwen русскую подсказку, которой нет у Belka. Каждый пример — новая независимая история; не переносить KV/chat context предыдущего вопроса.

Для binary GLUE достаточно малого отдельного output budget; текущий runner использует 8 токенов. Для свободных ответов предложен cap 512 new tokens и явно ограниченный объём ответа в условии. Перед заморозкой проверить, что prompt + output budget помещаются в 2048 у **обоих** токенизаторов; недопустима тихая обрезка длинных вопросов. Одинаковый cap не равен одинаковому объёму текста, поэтому отдельно учитывать количество символов и завершение по лимиту. Частые truncations — проблема дизайна, а не повод выборочно повышать лимит проигравшей модели после test.

Для каждой записи нужны: run_id, arm, model revision/checkpoint hash, tokenizer identity, benchmark hash, question_id/family_id, prompt hash, generation config, seed, raw answer, finish_reason, input/output tokens, elapsed time, error/attempt status. При HTTP-ошибке использовать заранее ограниченное одинаковое число технических retries, не выбирать лучший из нескольких содержательных ответов. Прерванный набор остаётся INCOMPLETE; для инфраструктурных сбоев показывать coverage и не выбрасывать сложные строки из знаменателя.

Один общий клиент может говорить с Qwen через localhost OpenAI-compatible endpoint, с Belka — через native server. Это **не использование внешнего OpenAI API**. Не использовать reference HF export Belka для заявлений о скорости: его карточка описывает FP32 full-prefix generation без оптимизированного KV-cache. См. [HF card](../export/HF_MODEL_CARD.md).

## 8. Метрики и ручная оценка

Не сводить качество к `pass_language`, нескольким ключевым словам или одному судье-LLM.

### Объективные задания

Показывать accuracy для каждого блока; CoLA — также MCC, sentiment — F1, остальные метрики по заранее выбранной task policy. Неправильный формат отмечать отдельно. Для строгого binary-протокола invalid answer считается неправильным для accuracy; нельзя задним числом извлекать выгодную цифру из длинного ответа. Сохранить текущую оговорку runner о неопределённости F1/MCC при invalid labels либо заранее определить другой единый scoring contract.

### Свободные ответы

Для всех 500 свободных заданий рекомендованы два независимых белорусскоязычных оценщика. Им скрывают модель и стадию, порядок ответов рандомизируют, разногласия разбирают по заранее описанному правилу. Отдельные шкалы:

- правильность/содержательная полезность: 0–4;
- качество белорусского языка: 0–4;
- выполнение инструкции: 0–2.

Ошибки, выдуманные факты, незапрошенный отказ, пустой ответ и смешение языков маркируются отдельно. Fluent Belarusian nonsense не является успешным ответом. Критерии допустимых вариантов публикуются до оценивания. LLM-judge допустим только как вспомогательная разметка с проверкой человеком; не использовать одну из сравниваемых моделей как единственного судью.

Основные результаты: вектор task accuracies, содержательная/языковая оценка свободных ответов, format adherence, hallucination/error/truncation rates и парные win/tie/loss. Не называть произвольное среднее heterogeneous scores официальным benchmark aggregate.

### Статистика

Сравнивать ответы попарно по question_id. Для интервалов разницы — paired bootstrap с сохранением категорий и кластеризацией по family/source, например 10 000 перевыборок. Для бинарного парного исхода — McNemar по discordant pairs; заранее определить основные сравнения и поправку на множественные вторичные тесты. Интервал по 1000 заданиям не измеряет разброс обучения по seed. Сильные выводы требуют независимых повторов обучения; один seed — демонстрационный опыт с явно ограниченной обобщаемостью.

### Оценка самого корпуса

Отдельно считать NLL/BPB на одних и тех же held-out текстах, не только ответы на вопросы. Token-level perplexity разных токенизаторов напрямую несопоставима. BPB вычислять по UTF-8 байтам одинакового payload, согласовать scoring masks, границы документов, BOS/EOS и доступный контекст; каждый text target должен учитываться ровно один раз. Это byte-normalized диагностика конкретных реализаций, а не доказательство одинакового receptive field при context=2048 разных токенизаторов. A0/B0 можно сравнивать и по PPL при неизменном tokenizer/protocol.

См. [объяснение зависимости perplexity от токенизации](https://huggingface.co/docs/transformers/perplexity).

## 9. Одна H200: ресурсы и последовательность

Все GPU-стадии выполняются последовательно, одним процессом на выделенном GPU. Не оставлять inference server в памяти во время следующего обучения. Не запускать восьмипроцессный `torchrun` и не подменять отсутствие VRAM CPU-offload без отражения этого в отчёте. Отдельные окружения baseline и Belka должны иметь собственные pinned dependencies.

[H200](https://www.nvidia.com/en-us/data-center/h200/) имеет 141 GB HBM3e в полной конфигурации. Для 1,54B BF16 веса — около 3,08 GB (арифметика 2 байта на параметр). У FP32 parameters/gradients и двух FP32 Adam moments — около 24,64 GB до activations, logits, temporary buffers и allocator. Это оценка компонентов, **не замер peak training memory**. На этом масштабе полный fine-tuning — разумный кандидат, но batch выбирается отдельным probe реального Qwen trainer. Belka probe не сертифицирует Qwen.

Последовательность после заморозки протокола: technical pilot на development → A0 → A1 → B0 → B1 → C0/C1 → единый blinded scoring и отчёт. Нужны отдельные имена run/model-tag и неизменяемые каталоги исходных весов/данных. Обучение не должно перезаписывать baseline или исходный corpus/tokenizer.

Числа времени в `docs/H200_TRAINING.md` являются сценарными оценками Belka, не замерами всего BE1000. Если сохраняется суммарный лимит 168 часов, он распределяется между всеми стадиями, пилотами, inference и резервом; нельзя выделить 168 часов независимо каждому запуску. После probe оценивать `время ≈ фактические предъявленные токены / измеренная скорость + evaluation/checkpoint overhead`. Для Qwen и Belka использовать разные реальные token counts и throughput. Никакое время окончания эксперимента этим документом не обещается.

## 10. Что ещё требуется реализовать для этого опыта

Не следует выдавать отдельные существующие команды за уже собранный orchestrator BE1000. Нужны ограниченные новые компоненты:

| Компонент | Критерий готовности |
|---|---|
| Frozen benchmark manifest | Ровно 1000 уникальных IDs, категории, family IDs, gold/rubric, hashes, отдельный development |
| Baseline CPT/SFT adapter | HF-модель и её родной tokenizer; prepared Parquet; правильные causal/assistant labels; budgets/checkpoints/resume; без записи в данные Belka |
| Единый collector | Проверка model/dataset/config identity, raw answers/finish reason, безопасное возобновление без перезаписи уже проверенных ответов |
| Scorer и blinded review export | Разные scoring contracts для GLUE, числовых и свободных ответов; coverage/errors; парные интервалы |
| Final report | A0/B1/C1 плюс A1/B0; все 1000 строк, ресурсы/экспозиция/ограничения, а не только удачные примеры |

Предлагаемые пути будущих файлов — `configs/experiments/be1000.yaml`, `eval/be1000/`, `experiments/be1000/`. Это план имён, **не команды, которые уже можно запускать**. До появления явного внешнего baseline trainer не передавать Qwen checkpoint в `scripts.base_train` или `chat_sft_be`: native Belka-архитектура и её checkpoint/tokenizer-контракты иные.

## 11. Как формулировать итог

Допустимый вывод после реальных измерений: «На зафиксированном BE1000 выбранная готовая модель изменила такие-то показатели после адаптации; Belka такого-то размера при таком-то бюджете дала такие-то показатели». Чистый вклад этапа корпуса подкрепляется B1 против A1 и B0 против A0, а не одним суммарным улучшением.

Недопустимо заранее обещать победу Belka, называть языковую эвристику точностью ответов, объявлять два tokenizer token budgets одинаковой экспозицией или утверждать, что сравнение доказывает превосходство архитектуры. Неудачный/нулевой эффект тоже является результатом при соблюдении протокола.

В этом коммите добавлен только данный протокол. Данные, токенизатор, профили, исходники trainer, weights и результаты измерений не изменены; эксперимент, тесты и аппаратные probes не запускались.
